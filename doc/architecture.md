# 架构

> 2026-10-23 修订：采用 PCL-Harmony 新增的跨启动器插件契约，取消原先自己的 Host.Pcl / Host.Ce 两层；不再按"闭源 / 开源 / CE"区分版本，改为"尝试性 hook，hook 失败就禁用对应功能"。

## 加载方式（采用 Harmony 的契约）

PCL-Harmony 提供两套加载方式，插件一份 DLL 可以同时运行：

| 宿主 | 运行时 | Harmony 的加载方式 |
|---|---|---|
| 官方闭源版、开源 Meloong 版（Harmony 里统称 `official`） | .NET Framework 4.8 | `exe.config` 里的 `appDomainManager` 注入 |
| PCL-CE（`ce`） | .NET 10 | 环境变量 `DOTNET_STARTUP_HOOKS`，需要用安装器生成的 `Run-with-PCL-Harmony.cmd` 启动 |

我们的 Mod 是一个 **netstandard2.0 插件**，实现契约里的 `IDeclarativePlugin`：

- `GetPatches(hostKind, hostVersion, host)` 只**描述**要打的补丁（`PatchSpec`：目标类型与方法、`prefix` / `postfix` / `redirect`、钩子的类型与方法名），由 Harmony 一侧执行。
- 插件**不引用 Harmony**，也不能自带 `0Harmony`、`PclHarmony`、`PclHarmony.Contract`。
- 钩子必须是公开的静态具名方法，不能是 lambda；按参数名绑定目标参数。
- 每个 `PatchSpec` 都写明 `TargetParameterTypes`，避免宿主在参数对不上时悄悄退回第一个同名重载。

## 项目结构

```
src/
  BetterPcl.Core/     netstandard2.0  功能逻辑、配置、日志抽象；不引用 PCL 类型，也不引用 Harmony
  BetterPcl.Plugin/   netstandard2.0  IDeclarativePlugin、钩子、尝试性 hook 与预检、安全模式
test/
  BetterPcl.Core.Tests/               针对 Core 的单元测试
```

`Core` 与 `Plugin` 是否要合成一个 DLL，取决于 Harmony 加载器对插件依赖的解析方式，等第一个骨架跑通后再定。

## 尝试性 hook（不区分版本）

- 每个功能声明自己需要哪些补丁点。`GetPatches` 里先用反射**预检**：目标类型是否存在、方法是否存在、参数类型是否匹配。一个功能的必需补丁点全部通过才启用；有任何一个失败，该功能整体禁用，并记录原因。
- 功能之间互相独立：一个功能 hook 失败，不影响其他功能。
- `hostKind` 只用来选择补丁目标（`official` 与 `ce` 的类型名不同），不用来判断"这是哪个版本"。
- 禁用的功能要让用户看得见：在日志里写明原因，并在界面里提示（见"提示与安全模式"）。

## 版本门禁与安全模式

- 面向 PCL 官方 / 开源版的支持范围是 `2.99.0.0` 及更新版本。CE 的版本号体系不同（目前参考源码是 2.15.1），CE 的支持范围怎么界定，待定。
- 契约本身没有版本声明机制，所以门禁在我们的 `GetPatches` 里做。
- **不支持当前版本时，不是直接返回空**，而是自动进入**安全模式**：
  1. 不应用任何功能补丁，只保留"显示提示"和"设置页入口"所需的最小补丁。
  2. 提示用户：插件不支持当前版本，已自动进入安全模式。
  3. 在设置页提供"强制启用"，由用户自己决定是否在不受支持的版本上使用。
- **兜底**：如果连提示和设置页的补丁都没能生效，就直接调用系统框架弹出消息框来提示，并告知用户在这种模式下连"强制启用"也做不到。

## 对 Harmony 已知缺陷的自我补偿

暂不向 Harmony 作者提改进，由我们自己防御：

| 缺陷 | 我们的做法 |
|---|---|
| 没有版本范围声明 | 在 `GetPatches` 里自己做门禁，并进入安全模式 |
| 参数对不上时退回第一个同名方法 | 每个 `PatchSpec` 都写 `TargetParameterTypes`，并在预检里用反射确认 |
| 所有插件共用一个补丁标识，出错时 `UnpatchAll` 会误撤别人的补丁 | 钩子内部全部 `try/catch`，不让异常冒出去；用功能开关停用功能，而不是依赖撤销补丁 |
| CE 宿主不清环境变量，更新器等子进程可能继承钩子 | 在 CE 上由我们的插件自己处理（具体做法待定，要先实测继承行为） |
| 插件完全受信、无签名校验 | 保持插件小而简单，便于逐行审核 |

## 云控与外连防护

分两层，详见 [roadmap.md](roadmap.md)：

1. 功能级安静停用：对每个依赖云控的功能不再发请求，界面置灰并提示"因禁用云控而失效"。
2. 外连白名单兜底：拦下白名单以外的连接，只记日志并提示一次。

目标是"尽可能防止"，不是正式审计。契约能否对 .NET 自带的类型（例如 `HttpClient`）打补丁尚未核实，核实之后再决定防护能做到哪一层；能控制的就控制，做不好再说。总开关先做成配置文件项，重启生效，界面内的开关后做。

## 凭据策略

- 仓库不存放任何密钥的值。
- CurseForge 官方 Key：**实际使用时的取得顺序**是 ① 读本机已安装的官方 CurseForge 启动器，② 照 Fjord 的做法联网取得，③ 用户手动填写；**开发顺序**是 ② → ① → ③。② 沿用 Fjord 的现有逻辑（不为 Windows 另做改造）；失败时要告诉用户可能的原因（官方包地址失效、偏移对不上、网络被拦、找不到字段等），不让用户一头雾水。缓存放用户本机并加密，日志里绝不出现 Key。
- 微软 Client ID：公开标识，按 Modrinth 的做法写成常量，不属于密钥；登录步骤的改法见 roadmap.md。
